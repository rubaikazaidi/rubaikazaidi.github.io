Beyond the Vault: What a Bank Internship Taught Me About APIs

How an unexpected introduction to financial technology changed the way I understand the applications and systems we use every day.

By Rubaika Zaidi • 5 min read • APIs & FinTech

I went into a bank expecting spreadsheets, paperwork and transactions. Instead, I found myself fascinated by the technology quietly connecting the financial world.

Before my bank internship, I had a fairly conventional idea of what happened inside a bank. I imagined rows of computers, employees managing transactions, endless spreadsheets and, of course, the occasional mention of a vault.

What I hadn't really considered was the technology working behind all of it.

During my internship, I came across something that changed how I looked at modern banking: APIs (Application Programming Interfaces).

I had encountered the term before while learning about programming, but it had always felt like one of those technical concepts you memorise without fully appreciating. Seeing its relevance in the financial sector made things click. I began to understand how applications that seem completely independent of one another can communicate, exchange information and work together almost instantaneously.

The Aha! Moment: How Do Apps Talk to Banks?

I'd always wondered how applications like Google Pay could display banking information and facilitate transactions without actually being banks themselves.

The answer, in many cases, involves APIs.

Think of an API as a messenger between two software systems. It allows one application to request information or a service from another without needing direct access to its internal workings.

For example, when you check your bank balance through a payment application, the application can send a request to the bank's server through an authorised interface. The bank verifies the request, checks the permissions and returns the required information.

All of this happens in seconds.

I found it fascinating that something as simple as tapping a button on my phone could trigger a series of communications between different systems, most of which I would never actually see.

Speaking the Language: A Little Bit of JSON

As I learnt more about APIs, I came across another concept: JSON, short for JavaScript Object Notation.

JSON is a lightweight format used to exchange information between applications. It organises data into key-value pairs, making it relatively easy for both humans and computers to understand.

For example, imagine a payment application requesting an account balance. A simplified request might look something like this:

Example API Request · JSON
{
  "account_id": "123456789",
  "action": "check_balance",
  "secure_token": "example_token"
}

Once the request has been authenticated and authorised, the server might return a response like this:

Example API Response · JSON
{
  "status": "success",
  "account_id": "123456789",
  "balance_available": 2500.00,
  "currency": "INR"
}

The application can then read the balance_available value and display it to the user.

What I found interesting was how such a small, structured piece of text could allow two entirely different systems to exchange meaningful information. No complicated interface was needed for the exchange itself; just a common format and a set of rules both systems understood.

The Invisible Shields: Keeping Financial Data Safe

Of course, understanding how quickly information travels raised another question for me: how do banks ensure that all this data exchange is actually secure?

After all, we're talking about financial information, where even a small security lapse can have serious consequences.

This is where authentication, authorisation and encryption come in.

APIs don't simply let every application access everything. They use credentials and access tokens to verify incoming requests and determine what information an application is permitted to access.

For example, an application authorised to retrieve an account balance should not automatically have permission to access unrelated banking information. This follows a security principle called least privilege: giving a system only the access it needs to perform its function.

Encryption provides another layer of protection by converting information into a format that cannot be easily understood by unauthorised parties while it is being transmitted.

It made me realise that designing an API isn't just about making two applications communicate. It's about making sure they communicate safely, with the right permissions and within clearly defined boundaries.

Why This Matters

One of my biggest takeaways from the internship was understanding how much modern banking depends on different systems working together.

Banks don't necessarily need to develop every application or service themselves. APIs allow them to integrate with external platforms, payment applications and fintech companies, making it possible for different technologies to work together without having to build everything from scratch.

As someone interested in computer science, this was particularly exciting.

Until then, I had mostly thought about programming in terms of writing code, building applications and making things work. The internship introduced me to another side of software development: designing the connections that allow those applications to function together.

A well-designed system doesn't necessarily have to do everything independently. Sometimes, its greatest strength lies in how effectively it communicates with other systems.

Precision Under Pressure

Interestingly, this brought me back to something I know quite well outside the world of technology: competitive rifle shooting.

Having spent years training and competing, I've learnt that precision often comes down to the smallest details. A slight change in posture, breathing or concentration can affect an entire shot.

I see a similar importance of precision in programming. A misplaced character, an incorrect parameter or an authentication failure can prevent an API request from working as intended.

The two experiences are obviously very different, but both have taught me the value of patience, consistency and paying attention to details.

Looking Beyond the Screen

Since the internship, I've started looking at everyday applications a little differently. When I use a payment app, I find myself wondering what requests are being sent in the background, what information is being exchanged and how different systems manage to communicate so quickly.

I went into the internship expecting to learn about how a bank operates. I came away with a much greater appreciation for the technology that makes modern banking possible.

More importantly, it changed how I think about computer science. Technology isn't always about what we see on our screens. Some of the most interesting work happens behind them, in the systems that quietly connect everything.

I don't just want to understand these digital bridges anymore. I want to learn how to build them.
